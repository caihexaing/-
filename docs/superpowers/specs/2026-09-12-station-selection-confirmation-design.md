# 12306 站点选择确认修复设计

## 问题

首页导航过程中，`ACTION_SET_TEXT` 将“汉口”或“潜江”写入输入框后，当前实现会把输入框文字等于目标站名直接当作“站点已选择”。在 12306 仍显示候选列表时，这只是搜索词，不是已确认的站点。后续页面树刷新后，自动化阶段与官方页面不一致，可能重复打开出发站并最终超时。

## 目标

- 输入站名、点击候选站、确认字段三步必须分别完成。
- 每次候选点击后重新读取无障碍树，不能使用点击前的旧树推进阶段。
- 出发站确认后只能进入到达站；到达站确认后才能进入日期。
- 候选缺失、不唯一、点击失败或字段未确认时，进入带具体原因的人工接管，不重复打开已处理字段。
- 不改变官方页面操作边界，不绕过登录、验证码、身份核验、风控、候补或支付。

## 方案

`OfficialSearchInteractor` 为每个站点维护短生命周期的选择状态：

1. `NEED_INPUT`：定位当前字段并输入任务站名。
2. `WAITING_CANDIDATE`：等待当前字段候选项，输入框文字不能使此阶段提前完成。
3. `CANDIDATE_CLICKED`：只派发一次唯一候选的点击，记录动作结果。
4. `WAITING_CONFIRMATION`：等待新页面树，确认候选页关闭、当前字段显示目标站名且另一字段未被修改。
5. `CONFIRMED`：返回 `DONE`，由服务推进到下一个字段。

精确匹配优先使用站点名称；对官方节点中带“站”等展示后缀的文本，只在去除受支持展示后缀后仍唯一时接受。不能用任意包含关系替代唯一匹配。候选节点的可点击父节点必须唯一且可操作。

`TicketAccessibilityService` 在 `DEPARTURE`/`ARRIVAL` 阶段收到 `WAITING` 时只等待页面刷新，不再次打开字段控件。每次点击后重新调用 `rootInActiveWindow`，并对当前字段、页面状态和选择状态做一致性校验。超时诊断只记录字段、候选数量、匹配类型、动作结果和确认结果，不记录账号、证件号、手机号、姓名或完整页面文本。

## 测试与验收

- 输入框文字等于目标站名但候选列表仍存在时，不能返回 `DONE`。
- 唯一候选点击后，下一棵树确认字段和页面状态后才返回 `DONE`。
- “汉口”候选完成后只能推进到“潜江”，不能再次触发出发站动作。
- “汉口站”这类受支持展示后缀能被唯一识别；多个同名候选必须失败并接管。
- 候选不出现、点击返回 `false`、字段确认不一致时均产生明确诊断并停止重复操作。
- 保留现有单元测试，并完成 Debug APK 构建；真机验收需观察出发站、到达站、日期三个阶段的页面树刷新和状态变化。
