# 车站选择查询顺序与诊断改进设计

## 背景

v0.4.27 在 12306 车站选择页先扫描全页候选，再确认顶部搜索框回读。页面默认的“常用车站”列表可能已经包含目标站名，导致候选分支反复等待，搜索框的 `ACTION_SET_TEXT` 永远不会发送。最新诊断已确认流程停在 `DEPARTURE`，没有进入日期、结果页或订单流程。

## 目标

- 车站选择页必须先确认唯一的顶部搜索框并写入目标站名。
- 只有同一输入框回读目标站名后，才允许扫描和点击过滤后的候选。
- 默认“常用车站/热门车站”列表不能作为过滤完成证据。
- 输入框节点重建或边界变化时安全重新绑定，并重新写入、重新回读。
- 车站选择阶段显式记录查询写入、回读、候选过滤和选择确认状态。
- 保持点击后刷新页面树、字段显示确认和人工接管边界，不改变日期、车次、席别和订单提交规则。

## 方案

`OfficialSearchInteractor.fillStation()` 按以下顺序执行：

1. 识别车站选择页和唯一顶部输入框。
2. 若输入框尚未回读目标站名，优先聚焦并发送一次 `ACTION_SET_TEXT`。
3. 等待同一输入框回读；节点重建时按稳定布局/语义重新绑定，并清除旧写入确认。
4. 输入确认后，仅从过滤结果或明确刷新后的候选容器中查找唯一目标站。
5. 点击候选一次，等待页面树刷新、选择页关闭和对应表单字段显示目标站。

状态使用 `WAITING_QUERY_WRITE`、`WAITING_QUERY_READBACK`、`WAITING_FILTERED_CANDIDATE`、`WAITING_CONFIRMATION`，并把状态、输入框 key、是否已写入/回读、候选作用域和数量写入脱敏诊断。

## 持久化诊断

在 `TicketTask` 中增加稳定页面状态、未知原因、车站查询阶段、写入/回读标志、候选作用域/数量及时间戳。`UNKNOWN` 仍可记录为最后一次事件，但不覆盖最后稳定页面。旧任务读取时使用默认值保持兼容，导出报告只包含这些状态字段，不保存账号、证件、手机号或支付信息。

## 验证

- 增加纯函数测试覆盖新状态和查询顺序。
- 保留现有车站选择确认测试，并增加“默认列表含目标站时必须先写入查询”的回归场景。
- 运行 `test` 和 `assembleDebug`；真机验收需验证汉口 -> 潜江场景中输入、回读、候选点击和表单回填的完整链路。

## v0.4.28 真机诊断补充

v0.4.28 的脱敏无障碍树确认：搜索框已回读“汉口”，但唯一候选的实际文本为“火车站 汉口站”。严格匹配器把该展示前缀当成站名的一部分，候选数量被记录为 0，因此没有派发候选点击。

同一输入框在 WebView 更新后从越界宽度收缩到屏幕内宽度；原身份键包含完整右/下边界，导致同一语义控件被误判为新节点。修复后的身份键优先使用 Android 33+ 的 `uniqueId`，回退时使用资源 ID、类名、左上位置和父容器结构，不把动态宽度作为身份依据。只有确实换成新节点时才清除写入/回读证据，并强制重新写入；同一输入框的尺寸变化继续沿用现有查询证据。

候选匹配只剥离有限的官方展示前缀（如“火车站”“车站”“高铁站”“动车站”“站点”），剥离后仍必须与目标站名或目标站名加“站”完全相等；“汉口南”等相近站名仍拒绝。新增对应的纯函数回归测试。

## v0.4.30 确认推进补充

实际运行中，出发站候选已唯一定位并派发点击，但 WebView 在第一棵回填表单树中仍短暂保留候选行。旧逻辑先看到候选数大于 0 就继续等待，未检查对应表单字段，导致 `DEPARTURE` 永远不能返回 `DONE`，终点站自然不会开始。修复后先核对选择页已关闭、快照已变化且目标字段已回填，再处理残留候选；只有缺少回填证据时才继续等待。

服务层的 `DEPARTURE` 和 `ARRIVAL` 都调用同一个 `handleStationField()`，由同一个 `OfficialSearchInteractor.fillStation()` 状态机完成输入框定位、`ACTION_SET_TEXT`、回读、候选过滤、单次点击和页面刷新确认。出发站确认后才切换 `ARRIVAL`，到达站确认后才切换 `DATE`，任何一步失败均不跨阶段盲目点击。

## v0.4.31 反向路线防护补充

诊断 `ticket-assistant-diagnostic-20260915-160122.json` 显示任务为“潜江 → 汉口”，但官方表单为“汉口 → 潜江”，且流程已经进入 `DATE` 并点击查询。根因是站点显示确认在字段关联缺失时退回全树唯一文本匹配，错误地把另一字段或查询历史中的站名当作当前字段。

修复后不再接受无字段关联的全树站名；查询前还会通过出发站/到达站各自控件做联合检查。路线不匹配或控件证据缺失时，服务清除旧的站点状态并重新执行共享的出发站、到达站流程，最多修复一次；仍无法确认则记录 `SEARCH_FORM_ROUTE_CONFLICT` 并人工接管，绝不点击“查询车票”。新增反向路线回归测试。
