# 12306 执行方案补充

## 结论

当前最关键的问题是把乘车日期误当成开售日期。任务模型必须把乘车时间和实际开售时间拆开；在开售日期未知时不能静默拼接乘车日期，也不能把任务显示为可执行。

## 时间模型

- `travelDateTime`：列车实际乘车日期/时间。
- `saleDateTime`：实际开售日期/时间，可为空。
- `saleTimeSource`：`OFFICIAL`、`USER_CONFIRMED` 或 `UNKNOWN`。
- 所有调度统一使用 `Asia/Shanghai`，设备时区变化后重新计算并提示。
- UI 同时显示“乘车时间”和“执行时间”，避免把两个日期混淆。

## 开售时间策略

1. 官方结果提供完整起售日期/时间时，解析并保存为 `OFFICIAL`。
2. 只有时分、没有日期时，显示“开售日期未知”，要求用户输入完整日期时间后才能启用。
3. 用户修正必须填写 `yyyy-MM-dd HH:mm`，标记为 `USER_CONFIRMED`，不能只修改 `HH:mm`。
4. `saleDateTime` 已过去时，先重新查询；确认已经开售则立即启动执行，否则提示用户重新配置。

## 调度与恢复

- 未开售任务才设置提醒、准备、开售三个闹钟。
- 已开售任务直接启动一次执行流程，不再设置未来闹钟。
- 开机、时间变化、时区变化和应用更新后重新注册闹钟。
- 闹钟触发后重新读取 `TaskStore`；任务不存在、停用或快照不一致时立即结束。
- 建议状态持久化为：`DRAFT -> ENABLED -> WAITING_FOR_SALE -> PREPARING -> OBSERVING -> TAKEOVER/PENDING_PAYMENT/RESULT_UNKNOWN/EXPIRED`。
- Activity 通过持久化 Flow 观察状态，不能只依赖内存中的 `storedTask`。

## 提交安全

- 开售触发时不能提前获取提交锁；只有在目标车次、席别和唯一成人乘车人全部核对通过、准备真正点击提交前，才事务性写入锁。
- 锁的 key 至少包含任务 UUID、`saleDateTime`、`travelDateTime` 和车次号。
- 点击后无论崩溃、超时还是结果不明，都保持锁；恢复时只能提示用户到官方订单页核对，禁止自动重试。
- 只有识别到新订单号、日期、车次、乘车人、席别和待支付金额，才能进入 `PENDING_PAYMENT`。

## 官方 App 与无障碍边界

- 只校验已验证的包名和签名；不能假设启动后处于查询页。
- 启动页、活动弹窗、登录失效、验证码、滑块、身份核验、风控、候补协议和未知页面都进入 `TAKEOVER`，停止自动动作并通知用户。
- “立即测试打开官方 12306”只验证启动，不应暗示会自动下单。
- 无障碍识别应返回明确页面状态和超时原因，不能只按“支付/订单”等普通词做全局误判。

## 验收用例

- 乘车日与开售日不同；开售日期未知禁止启用；已开售任务立即执行。
- 进程被杀、重启、时区变化、闹钟重复触发、任务停用和应用更新恢复。
- 官方 App 启动页/活动弹窗/登录/验证码/身份核验/未知页面均能安全接管。
- 同名或无匹配乘车人停止；提交点击后崩溃或结果不明不重复提交。

## 实施顺序

先改数据模型、TaskStore、TaskScheduler 和状态持久化；再实现已开售立即执行和恢复；随后做页面识别与人工接管；最后才在测试桩上实现自动选择和提交。真实行程不应作为反复回归测试样本。
