# 12306 结果页分类与站点确认修复设计

## 范围

本批只处理两个阻塞主流程的问题：

1. 查询结果列表同时包含车次、席别和“预订”时，被误判成席别选择页。
2. 站点输入文字、候选点击和最终字段确认之间证据不足，可能重复打开出发站或提前推进阶段。

本批不改冷启动启动策略、进程恢复、服务器时间、旁路查询、提交闸门和支付流程。验证码、登录、身份核验、风控、候补协议和支付仍由官方页面及用户处理。

## 方案一：页面分类优先结果证据

`PageStateClassifier` 保留订单确认、处理中、明确失败等高优先级状态，然后优先识别查询结果证据，再识别席别选择页。查询结果证据至少包含可识别车次以及结果列表语义（车次/余票/筛选条件/路线结果等），并允许同一文本同时出现“二等座”和“预订”。席别页只有在没有结果列表证据且存在席别选择语义与继续操作控件时才成立。

新增文本夹具覆盖：

- 结果列表包含 `D5995`、路线、日期、`二等座`、`预订`，必须为 `SEARCH_RESULT`。
- 席别选择页包含“选择席别”、`二等座`、`下一步`，且无结果列表语义，必须为 `SEAT_SELECTION`。
- 结果加载/部分结果仍保持 `SEARCH_RESULT_LOADING` 或 `SEARCH_RESULT_PARTIAL`。

如果证据不足，保持部分结果或未知状态并等待/接管，不通过“席别 + 预订”单独猜测。

## 方案二：站点选择的证据状态机

`OfficialSearchInteractor` 为当前字段保存以下短生命周期状态：

- `IDLE`：尚未开始该字段。
- `WAITING_CANDIDATE`：已输入或打开字段，等待候选项；输入框文字相等不能完成。
- `WAITING_CONFIRMATION`：APK 已点击唯一候选，等待新的无障碍页面树。
- `CONFIRMED`：只有点击前后页面快照发生变化、候选/选择器从可见变为不可见、目标字段容器显示目标站名，才完成。

点击前保存脱敏页面快照指纹和候选证据。点击后每次都重新计算候选、选择器可见性、字段容器值和快照指纹；不再把确认阶段的候选集合强行置空，也不允许仅凭输入框文字完成。若候选从未出现而字段文字自行变化，保持等待并最终进入人工接管。候选不唯一、点击失败或确认字段属于另一站点时立即接管。

已存在且未处于选择器中的预填站点仍可作为初始 `IDLE` 状态完成；一旦 APK 派发了输入或候选点击，必须经过相应确认状态，不能回退到预填捷径。

诊断只记录字段、阶段、候选数量、选择器状态、快照是否变化和 `DONE/WAITING/FAILED`，不记录账号、证件号、手机号、姓名或完整页面文本。

## 测试与验收

- 页面分类回归测试覆盖结果列表与席别页的重叠文本。
- 站点纯逻辑测试覆盖：输入文字不能确认、未发生快照变化不能确认、候选点击后快照变化并字段匹配才能确认、候选不唯一不能继续。
- 保留现有提交和待支付证据测试。
- `testDebugUnitTest` 和 `assembleDebug` 必须通过。
- 真机验收观察：汉口候选点击后只推进到潜江；潜江完成后进入日期；结果列表不会进入席别页；任一证据缺失时显示具体人工接管原因。
