# v0.2.9 APK 审查与开售状态改进要求

## 结论

GitHub Release `v0.2.9` 的 APK 已下载并核对 SHA-256：

```text
787c0793dccd58a02bfa9861e20f892e0dabfcee74133726058771211570b174
```

包名、版本号、SDK、权限和 APK 完整性基本正常；此前“把乘车日期误当成开售日期”的问题已经修复。但当前版本仍属于实验版本，不能保证在真实 12306 页面中稳定完成下单。

## 优先级问题

### P0：发布包仍是 Debug APK

APK Manifest 中存在 `application-debuggable`。发布包应使用正式 Release 构建和固定签名，不应上传 `app-debug.apk`。

发布前验收：

- `debuggable=false`；
- 使用固定 Release keystore 签名；
- 自动更新的签名校验与正式签名一致；
- 使用正式应用图标，而不是 `@android:drawable/ic_dialog_info`；
- 用 `apksigner verify --verbose --print-certs` 检查签名。

### P1：未知页面和图片弹窗会让无障碍流程静默卡住

当前服务只识别验证码、登录失效、身份核验、风控和待支付关键词。12306 启动页、活动图片弹窗、公告、更新提示、网络错误、首页或 WebView 加载失败可能既不会被识别，也不会进入人工接管。

建议建立明确页面状态：

```text
LAUNCHING / HOME_PAGE / SEARCH_RESULT / SEAT_SELECTION
PASSENGER_SELECTION / ORDER_CONFIRM / PENDING_PAYMENT
UNKNOWN_PAGE / TAKEOVER
```

任何无法确认页面类型的情况都应停止自动点击，保存原因并通知用户。

### P1：90 秒结果超时过短

当前找到车次后约 90 秒即转为 `RESULT_UNKNOWN`。用户处理弹窗、登录、验证码或身份核验可能超过 90 秒，导致无障碍服务提前停止。

建议按页面状态分别计时；人工接管状态不应自动结束。提交结果不明时保持提交锁，只提示用户去官方订单页核对，禁止自动重试。

### P1：查询请求频率和会话策略需要收敛

当前轮询会反复初始化 12306 会话，约每 8 秒查询一次，容易触发限流或风控。建议复用 Cookie，会话失败时重新初始化；正常间隔提高到 15～30 秒，采用指数退避，遇到限流立即停止。

### P1：无票席别仍可保存

配置页面不应允许选择或保存 `无`、`无票`、`--`、`*` 等不可购买状态。运行时席别变为不可用时，应显示明确状态并结束或等待人工操作。

### P1：Android 15/16 后台恢复风险

开机、时区变化或应用更新后，广播接收器可能直接启动前台 `dataSync` 服务，系统可能抛出 `ForegroundServiceStartNotAllowedException`。建议恢复时重建闹钟并发送通知，由用户点击通知进入执行；同时捕获并记录前台服务启动异常。

### P1：精确闹钟权限降级提示不足

没有精确闹钟权限时当前代码会退回非精确闹钟，但界面仍显示任务正常启用。建议抢票任务在未授权精确闹钟时禁止启用，或明确标记“降级调度，可能延迟”。同时检查电池优化和厂商后台限制。

### P2：无障碍服务应限定官方包名

在 `accessibility_service_config.xml` 增加：

```xml
android:packageNames="com.MobileTicket"
```

代码中的包名过滤仍应保留，作为第二层保护。

### P2：准备阶段服务生命周期和回归测试

开售前准备阶段成功唤起官方 App 后应及时结束准备服务，避免长期保留前台通知。另需增加脱敏无障碍树测试，覆盖弹窗、登录、验证码、同名乘车人、字段不一致、订单确认和待支付页面。

## 开售日期时间业务规则

开售日期时间不能简单地设为“始终必填”。必须区分以下两种情况。

### 情况一：车票已经开售

- 用户不需要填写开售日期时间；
- 保存前重新查询一次官方车次数据；
- 确认目标车次和所选席别已经有票后，标记 `saleState=ALREADY_ON_SALE`；
- `saleDateTime` 可以为空；
- 保存任务后立即进入执行流程，不设置未来开售闹钟；
- 如果查询失败或无法确认“已开售”，不能默认当成已开售。

### 情况二：车票尚未开售

- 只有确认尚未开售时，才要求填写开售日期时间；
- 必须填写完整格式 `yyyy-MM-dd HH:mm`；
- 统一使用 `Asia/Shanghai` 时区；
- 时间必须晚于当前时间；
- 校验通过后标记 `saleState=NOT_YET_ON_SALE`，再设置提醒、准备和开售闹钟；
- 已填写但时间已过去时，应重新查询确认是否已开售，不能直接按未来任务处理。

### 查询不明确

查询失败、接口返回异常、车次状态无法判断时标记：

```text
saleState=UNKNOWN
```

此时禁止盲目执行，提示用户重试或人工确认。

## 推荐数据模型

```kotlin
enum class SaleState {
    ALREADY_ON_SALE,
    NOT_YET_ON_SALE,
    UNKNOWN
}
```

`TicketTask` 建议至少保存：

```text
travelDate       乘车日期
saleState        开售状态
saleDateTime     可为空；仅 NOT_YET_ON_SALE 时必填
saleTimeSource   OFFICIAL / USER_CONFIRMED / UNKNOWN
taskId           任务唯一 ID
status           持久化执行状态
```

保存和调度逻辑应满足：

```text
查询确认已开售
  -> ALREADY_ON_SALE
  -> saleDateTime 可为空
  -> 立即执行

查询确认尚未开售
  -> NOT_YET_ON_SALE
  -> saleDateTime 必填且必须是未来时间
  -> 设置闹钟并等待

查询失败或无法判断
  -> UNKNOWN
  -> 禁止执行，提示重试
```

需要同步更新 `TicketTask`、`TaskStore`、`TaskTiming`、配置页面、`TaskScheduler`、任务恢复和旧版本数据迁移。旧任务没有 `saleState` 时，不应静默视为已开售；应进入 `UNKNOWN` 或要求用户重新确认。

## 必须补充的验收用例

- 已开售且 `saleDateTime=null`：可以保存并立即执行；
- 未开售且时间为空：禁止启用；
- 未开售填写过去时间：重新查询，确认已开售才可转为立即执行，否则拒绝；
- 查询失败：不能默认已开售；
- 乘车日期和开售日期不同：调度不混淆；
- 重启、时区变化、应用更新和重复闹钟：任务状态和任务 ID 校验正确；
- 12306 启动弹窗、首页、未知页面：进入人工接管，不盲点；
- 同名或找不到乘车人：停止；
- 提交后崩溃或结果不明：提交锁保持关闭，不自动重试；
- 识别到订单号、日期、车次、席别、乘车人和待支付金额后，才进入 `PENDING_PAYMENT`。

## 推荐实施顺序

1. 先修复 Release 构建、签名和 Debug 标记。
2. 再引入 `SaleState`，修改任务保存、调度、恢复和迁移。
3. 增加未知页面接管、弹窗处理提示和分阶段超时。
4. 降低查询频率并复用会话，完善限流停止策略。
5. 修复 Android 15/16 后台恢复与精确闹钟提示。
6. 最后用脱敏无障碍树测试验证页面识别；真实支付、验证码和风控始终由用户处理。
