# 12306 任务信息自动查询设计

## 目标

让任务中已经确认的日期、出发站、到达站、车次、席别和乘车人真正成为官方 12306 操作的输入，而不是要求用户先手动查询到结果页再进行校验。

目标流程为：

```text
任务信息
  -> 启动官方 12306
  -> 自动填写日期、出发站、到达站
  -> 选择精确车站并查询
  -> 在目标车次范围内选择席别并预订
  -> 选择唯一同名乘车人
  -> 校验订单字段并点击“提交订单”
  -> 等待官方结果并停在待支付页面
```

验证码、滑块、登录失效、身份核验、候补协议、风控、未知页面和支付仍然由用户处理。自动化不能输入密码、绕过验证或支付。

## 当前问题

`OfficialAppLauncher` 只能调用 `getLaunchIntentForPackage("com.MobileTicket")`，Android 启动 Intent 不会把任务日期、站点或车次可靠地传给官方 App。当前无障碍服务从 `SEARCH_RESULT` 阶段开始，并要求无障碍树一次性包含日期、站点、车次和席别；因此任务数据虽然已保存，却没有驱动首页查询。

本次诊断中的 `SEARCH_RESULT + 最近动作为空 + 提交锁未锁定` 表明服务只观察到一个结果类事件，没有成功执行任何选择动作。实现必须把“启动后的页面导航和查询表单填写”纳入状态机。

## 设计

### 1. 执行状态

在现有状态基础上增加页面操作阶段，状态必须持久化到 `TaskStore`，并在每次动作后记录脱敏事件：

- `WAITING_OFFICIAL_PAGE`：等待官方 App 页面事件。
- `OPENING_SEARCH`：官方 App 已启动，正在定位车票查询入口。
- `FILLING_DEPARTURE`：填写出发站并等待精确候选项。
- `FILLING_ARRIVAL`：填写到达站并等待精确候选项。
- `FILLING_DATE`：填写或选择乘车日期。
- `SUBMITTING_SEARCH`：点击查询并等待结果页。
- `VALIDATING_SEARCH_RESULT`：核对查询上下文和目标车次。
- `SELECTING_TRAIN_SEAT`：在目标车次容器内选择席别并点击预订。
- `SELECTING_PASSENGER`：选择唯一同名乘车人。
- `VALIDATING_ORDER`：核对订单确认页可见证据。
- `SUBMIT_ACTION_SENT`：已向官方页面派发提交动作。
- `WAITING_SERVER_RESULT`：等待官方服务器返回结果。
- `PENDING_PAYMENT`、`SUBMIT_REJECTED`、`TAKEOVER`、`RESULT_UNKNOWN`：终态。

如果官方 App 已经处于查询结果页，流程可以从 `VALIDATING_SEARCH_RESULT` 继续；如果处于首页或车票查询表单，则从 `OPENING_SEARCH` 开始自动填写。不能再把“用户手动停留在结果页”作为前置条件。

### 2. 官方页面交互

新增一个只负责官方车票查询表单和结果定位的交互组件，由 `TicketAccessibilityService` 驱动状态转换。组件使用以下信号联合定位控件，并按优先级尝试：

1. 稳定的 `viewIdResourceName`、控件类名、可编辑/可点击属性；
2. 标签文本、内容描述和相邻节点关系；
3. 同一表单或车次容器内的层级关系。

不得依赖固定屏幕坐标，也不得点击全页面第一个同名文本。找不到唯一控件、控件不可操作或动作结果无法验证时，进入 `TAKEOVER` 并说明阶段和原因。

#### 首页和表单

- 定位“车票/查询”入口；如果已在车票表单，直接复用。
- 出发站和到达站分别清空后写入任务站名，等待候选列表，再只接受名称完全相等的候选项。
- 日期优先使用可编辑日期节点；若官方页面使用日期选择器，则打开选择器，按任务年月日选择并验证确认结果。
- 点击“查询”后等待新的窗口内容事件，最多等待页面操作超时；不能用固定短延迟直接假定查询完成。
- 每个字段保存“已写入/已选择/已验证”的内部证据。官方页面文本不暴露某个字段时，可以使用同一会话中成功的控件动作证据，但不能在完全没有动作结果时放行。

#### 结果页和车次

- 先按车次号精确匹配节点，再向上寻找包含任务出发站、到达站或对应时刻的最小车次容器。
- 只在该容器内寻找任务席别及其对应的“预订”控件；席别和预订按钮必须属于同一车次上下文。
- 支持结果页直接显示席别按钮和进入详情后再选择席别两种布局。
- 点击后必须收到页面状态变化或明确的下一阶段控件，不能把 `performAction=true` 当作页面已切换。
- 结果页没有目标车次、席别不可购买、车次容器不唯一或页面改版导致关系无法确定时，停止并人工接管。

#### 乘车人、订单和提交

- 在乘车人页只匹配与任务姓名完全相等的文本节点；多个同名、没有匹配或无法确认乘客类型时停止。
- 订单确认页采用累积证据核对日期、车次、席别和乘车人，不要求所有字段必须出现在同一棵树中，但必须在连续页面事件中得到可靠证据。
- 只有找到唯一可点击的“提交订单”控件后才获取 `PersistentSubmitGate`。
- 点击返回 `false` 时释放本次锁并记录“点击未派发”；返回 `true` 只更新为“已发送提交点击，等待官方确认”。
- 提交后识别处理中、排队、待支付、席位不足、重复订单、网络错误和验证页面。确认订单号、日期、车次、席别、乘车人和金额的待支付证据后才进入 `PENDING_PAYMENT` 并停止服务。

### 3. 状态和失败处理

每次官方事件都记录：页面分类、当前阶段、动作名称、动作结果、事件时间和连续失败次数。记录只允许包含字段类型和脱敏原因，例如“已填写出发站”“日期选择器未找到”，不得保存姓名、账号、证件号、订单号、金额或完整页面文本。

以下情况立即进入 `TAKEOVER`，停止后台查询和自动点击：

- 登录失效、验证码/滑块、身份核验、实名认证、风控或候补协议；
- 官方活动/公告/升级弹窗；
- 首页、未知页面、空无障碍树连续超时；
- 表单字段、候选车站、目标车次、席别、乘车人或提交按钮不唯一；
- 页面动作未派发或动作后没有可验证的页面变化。

提交点击之后不因短暂未知页面自动重试。提交锁保持有效，只有用户在官方订单页核对后重新创建任务，才允许再次尝试。

### 4. 任务快照一致性

自动化开始时保存任务快照键，至少包含 `taskId`、乘车日期、车次号、出发站、到达站和席别。服务收到事件时重新读取任务并比较快照；如果任务被编辑或诊断文件来自不同任务，立即停止并显示“任务信息已变化，请重新启动”。

诊断报告继续保留 `train`、`date`、`from`、`to`、`seat` 等非敏感目标字段，方便核对；若截图和诊断中的车次不一致，应优先按快照一致性处理，不继续自动点击。

### 5. 版本和发布策略

实现完成后先发布新的诊断预发布版本，不直接替换正式更新通道。版本号递增，Release 说明明确：自动填写依赖官方 12306 当前页面结构，尚未完成用户设备上的真机闭环时不得宣称可靠抢票。

正式发布前必须完成同一 Android 设备和官方 App 版本上的可取消测试：

```text
首页/表单 -> 自动填写 -> 查询结果 -> 车次/席别 -> 乘车人 -> 订单确认 -> 提交后状态
```

支付、验证码、身份核验和风控不纳入自动化验收。

## 测试验收

### 单元测试

- 表单字段和车站候选项的精确匹配、空值、同名和重复候选。
- 日期的多种官方显示格式与任务日期的转换。
- 车次容器、席别行和“预订”按钮的层级关联，拒绝跨车次匹配。
- 已有结果页、首页、弹窗、登录、验证码、未知页面的状态分类。
- 页面动作成功/失败、冷却、超时、提交锁获取和失败释放。
- 任务快照变化、旧任务恢复和诊断脱敏字段。

### 脱敏无障碍树夹具

为首页、站点候选、日期选择器、查询结果、席别页、乘车人页、订单确认页、处理中、待支付和各类人工接管页面建立最小化夹具。夹具不得包含真实姓名、证件号、账号、订单号或支付信息。

### 真机验收

在真实设备上确认：无障碍服务重启、应用切后台、慢加载、返回键、活动弹窗、页面改版和余票瞬时变化均不会盲点或重复提交。没有真机验收前，自动查询功能只能作为诊断版本提供。

## 非目标

- 不调用未公开的下单接口，不绕过 12306 的登录、验证码、身份核验、风控或候补协议。
- 不自动输入密码、短信验证码或支付信息。
- 不自动完成支付。
- 不通过固定坐标或截图识别代替可验证的无障碍节点关系。
