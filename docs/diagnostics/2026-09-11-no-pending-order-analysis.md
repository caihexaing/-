# 12306 无待支付订单：原因分析与修复建议

## 结论

截图中的“已进入观察阶段”和“已找到目标车次 D353”不代表订单已经提交。

当前 `v0.3.1` 的实际链路是：后台余票接口发现目标车次和席别可购买 → 将任务状态写为 `OBSERVING` → 只启动官方 12306 的主入口 → 停止后台查询服务。只有后续无障碍服务成功识别官方页面、逐页点击，并且 12306 服务端接受“提交订单”后，待支付列表才会出现订单。

截图一直停留在 `OBSERVING`，官方 12306 又没有待支付订单，最可能说明流程根本没有走到有效提交；其次才是点击提交后被 12306 拒绝。不能把这个状态解释成“已经下单”。

## 已确认的代码证据

1. `TicketAutomationService.kt` 在查询到余票后，先写入 `OBSERVING`，然后调用 `OfficialAppLauncher.launch()`，随即 `stopSelf()`。这里没有任何下单请求。
2. `OfficialAppLauncher.kt` 只执行 `getLaunchIntentForPackage("com.MobileTicket")`，不能携带出发站、到达站、乘车日期，也不能保证进入目标查询结果页。
3. `TicketAccessibilityService.kt` 启动时却直接假定官方 App 已在 `SEARCH_RESULT`，并依次期待：查询结果 → 席别选择 → 乘车人选择 → 订单确认。官方 App 若停在首页、旧页面或不同版本页面，这条状态机就无法继续。
4. 无障碍树为空时，代码直接 `return`；找不到车次、席别或“提交订单”控件时，多处也是静默返回，所以任务可能长期显示 `OBSERVING`，用户看不到真实失败原因。
5. 当前点击逻辑只按可访问文本寻找第一个车次节点，再向上找最多五层可点击父节点。它没有把目标车次卡片、目标席别行与对应“预订”按钮绑定，也没有滚动、控件 ID 或页面结构校验，和真实 12306 页面很容易不匹配。
6. 一次性提交锁在真正点击前就被写入。如果找到“提交订单”文本，但 `performAction(ACTION_CLICK)` 返回失败，锁仍然保留，实际没有提交却会被视为“已经尝试提交”。
7. `ACTION_CLICK=true` 只表示系统接受了点击动作，不表示 12306 服务端创建订单。当前代码没有完整识别排队中、席位不足、提交失败、重复订单、确认弹窗等提交后状态。
8. 待支付成功校验要求订单号、日期、车次、席别、乘车人和金额同时出现在一棵无障碍树中，条件可能比真实页面严格。它可能把真实订单标成“结果不明”，但无法解释官方列表完全没有订单；官方列表为空仍说明提交未完成或被拒绝。
9. 现有 30 个单元测试全部通过，但都是纯文本/规则测试，没有真实 12306 无障碍树、真机 UI 或端到端下单测试。此前发布记录也明确写明尚未连接真实手机完成完整下单验证。

## 本次现象的可能性排序

1. **最高概率：只打开了 12306 首页，没有进入正确的查询结果页。** 启动器没有深链或自动填写行程，但状态机直接从查询结果页开始。
2. **高概率：无障碍服务没有真正工作或拿不到页面节点。** “打开无障碍设置”不等于已经启用服务；12306 页面也可能有节点为空、控件不可点击或事件未触发的情况。截图仍为 `OBSERVING`，符合服务没有写入任何下一阶段状态的表现。
3. **高概率：真实 12306 页面结构与当前假设不一致。** 代码可能点击了车次详情而不是席别对应的“预订”，或者找不到精确席别/乘车人/提交按钮。
4. **中概率：点击提交失败，但提交锁已经提前锁定。** 此时不会产生订单，还可能阻止后续重试。
5. **中概率：点击已发出，但 12306 返回排队、无票、风控、弹窗或提交失败。** 当前状态机没有覆盖这些页面。
6. **低概率：检查了不同 12306 账号、日期或订单入口。** 应确认官方 App 当前账号与任务乘车人对应，并检查“未完成订单/待支付订单”。

## 建议的修复顺序

### P0：先修正状态和诊断，禁止继续误报

- 将 `OBSERVING` 文案改为：“后台查询发现余票，尚未提交订单；等待官方 12306 页面操作”。
- 新增并持久化细分阶段：
  - `WAITING_OFFICIAL_PAGE`
  - `VALIDATING_SEARCH_RESULT`
  - `SELECTING_TRAIN_SEAT`
  - `SELECTING_PASSENGER`
  - `VALIDATING_ORDER`
  - `SUBMIT_ACTION_SENT`
  - `WAITING_SERVER_RESULT`
  - `PENDING_PAYMENT`
  - `SUBMIT_REJECTED`
  - `TAKEOVER`
- 每一步记录时间、页面分类、找到的控件、点击返回值和停止原因；页面树为空或连续找不到目标控件时，必须进入 `TAKEOVER`，不能静默卡在观察状态。
- 任务页显示：无障碍服务是否启用、最后一次收到 12306 事件的时间、当前自动化阶段、提交锁状态。
- 增加“导出脱敏诊断”功能，保存页面类型、控件文本摘要和动作结果，不保存证件号、账号或支付信息。

### P0：修复官方 App 入口与执行前置条件

短期可靠方案：不要假设启动官方 App 后就是查询结果页。要求用户先在官方 12306 手动查询好完全一致的日期和路线，并停留在结果页；App 验证日期、出发站、到达站、车次和席别全部一致后才开始点击。

若要自动化首页查询，则必须单独实现首页状态：填写/选择出发站、到达站、日期并点击查询，然后验证结果页；不能只使用主启动 Intent。任何字段或页面无法确认都立即人工接管。

### P0：按真实控件结构选择车次和席别

- 不再点击页面中第一个匹配车次号的文本。
- 先定位目标车次卡片，再在该卡片内定位目标席别行和与之对应的“预订”按钮。
- 使用控件 ID、类名、层级关系、可点击性和文本联合匹配；支持滚动查找。
- 点击后必须等待并验证目标页面已经切换，不能只靠固定 900ms 冷却。
- 将官方 12306 当前版本每个关键页面的脱敏无障碍树保存为测试夹具。

### P0：修复提交锁和提交结果语义

- 找不到可点击的“提交订单”控件时不得获取提交锁。
- 可以在点击前写 `SUBMIT_INTENT` 防止进程崩溃后重复点击，但如果 `performAction` 明确返回 `false`，应记录“点击未派发”并安全解除本次锁。
- 点击返回 `true` 后只显示“已发送提交点击，等待 12306 确认”，不能显示“已提交订单”。
- 提交锁只有在以下情况之一后才能由用户显式处理：识别到真实待支付订单；识别到明确失败且确认没有生成订单；用户在官方订单页核对后选择“确认无订单并重新建任务”。

### P1：补齐提交后页面状态

至少识别：处理中/排队中、提交成功、待支付、余票不足、订单失败、重复订单、验证码/滑块、身份核验、风控、网络错误、确认弹窗、未知页面。

待支付确认可分两步：先识别“待支付/支付倒计时/订单号”等强证据，再引导或辅助打开官方待支付订单列表，对日期、车次和乘车人做最终核对。不要要求所有字段必须同时出现在同一屏。

### P1：真机验收后再发布

- 在与用户相同的 Android 16 设备和当前官方 12306 版本上采集脱敏页面树。
- 使用非紧迫、可取消的真实行程完成一次：查询结果 → 预订 → 乘车人 → 订单确认 → 提交后状态 → 官方待支付列表。
- 验证无障碍服务重启、应用切后台、页面加载慢、弹窗和余票瞬时变化。
- 在完成真机闭环前，版本说明应明确标为实验性辅助，不宣称能够可靠自动生成订单。

## 用户当前可以怎样验证

1. 在系统无障碍服务列表中确认“行程助手”开关本身已开启，而不只是打开过设置页。
2. 在官方 12306 中确认登录的是正确账号，手动查询任务中的日期、路线和 D353，并停留在查询结果页。
3. 保持手机解锁、屏幕常亮，再启动任务并观察是否实际发生选车次、选席别、选乘车人和点击提交。
4. 只要官方页面没有出现订单确认/处理中/待支付等变化，就应判定为“未下单”，不要依据辅助 App 的 `OBSERVING` 状态判断成功。
5. 在代码修复前不建议反复用真实行程测试；提交锁与未知结果处理尚不够可观测，可能造成重复风险或错误锁定。

## 下一版建议

建议先做 `v0.3.2-diagnostic`，目标不是继续增加点击动作，而是把真实失败点完整记录出来，并修正观察状态文案、页面前置校验和提交锁。拿到一套真实 12306 页面树与真机日志后，再实现并验证 `v0.3.3` 的页面适配。
